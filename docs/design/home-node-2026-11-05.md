## 0. Verdict up front

1. **This is not the Raspberry Pi memo of 2026-09-30.** That design ([`breakout-raspberry-pi-scoping-2026-09-30.md`](../research/breakout-raspberry-pi-scoping-2026-09-30.md), [`breakout-r2-home-device-plan-2026-09-30.md`](../research/breakout-r2-home-device-plan-2026-09-30.md)) used a home box as an **egress tunnel for the VM's browser** to get around a block on our datacenter address. The operator declined it ("I don't want this solution", 2026-09-30 16:16Z). **This node routes nothing for the VMs.** Its network identity is its own: a device on the home network making its own connections.
2. **The strongest case for a home node is not the Breakout executor.** The executor is the *hardest* and *least certain* job (§ 2: emulator fingerprint, Android kernel modules, Breakout's agreement unread). The independent-watchdog and off-Oracle-backup jobs (§ 3) are cheap, low-risk, and fill real gaps.
3. **Recommendation: GO on a minimal node, infra jobs first** (watchdog + encrypted backup target), on a mini-PC-class box so the executor option stays open; **no executor work until Breakout answers** (§ 6).
4. **Security stance:** outbound-only, pull-based, holds the smallest possible secrets, backups encrypted so the box cannot read them, and a written "stolen box" revocation list (§ 4).
5. **Not a babysitting project:** one physical setup session, then it updates, restarts and reports itself (§ 5).

**Power and storage notes**
- **SD wear.** A microSD card dies from constant small writes (logs, DB, browser profile). For watchdog-only duty the write rate is tiny; for anything with a database or a browser profile, use an SSD (mini-PC) or Pi 5 + NVMe, or a high-endurance card with logs to RAM. The 2026-09-30 memo reached the same conclusion for L3 (skip NVMe when the Pi barely writes) and for L1 (browser: buy it).
- **UPS question.** The weak link in a home setup is usually the router/ONT, not the node: a UPS on only the node keeps a box alive that has no internet. If a UPS is bought, put the **ONT + router + node** on it (price not verified; ~$50-100 ESTIMATED for a small unit). A node that is off during a home power cut is acceptable **only if** its silence is itself detected (§ 3.1, "who watches the watcher").
- **Ethernet over Wi-Fi.** The operator said "hooked up to my Wi-Fi". Wi-Fi works for the watchdog and backup jobs, but Ethernet is more reliable for a box that must be always-on; the question is in § 6.
- **Other costs:** a microSD/USB stick for install, an Ethernet cable; nothing else.

## 2. Can it host the breakout_2 executor?

### 2.1 What the executor needs (carried over from the first spec)

An Android WebView app ("JTA Executor") whose JS drives the Breakout terminal, a login via emailed number-match read from a dedicated Gmail inbox over IMAP, a foreground service/watchdog, "Display over other apps" for bring-to-front, and the operator's own device token pinned to `breakout_2`. See [`phone-exec-offdevice-2026-11-05.md`](phone-exec-offdevice-2026-11-05.md) § 1. The APK is plain Kotlin/JVM: `app/build.gradle.kts` has **no NDK or ABI-filter settings** (grep for `abi|ndk` found only `minSdk 26 / targetSdk 34`), so the same APK should run on arm64 and x86-64 Android images. **Not build-verified for x86-64**; CI builds one debug APK today.

### 2.2 Venue findings that still bind (no spoofing)

- A **second honest device on the home network** is the only version we consider: its own identity, its own login, the home IP, a stock user agent. **No cloning of an Android ID, Build fingerprint or attestation; no masking of an emulator; no residential-proxy tricks.** If the venue or Cloudflare challenges an emulator, the option simply fails.
- **Breakout's binding agreements are still unread** (Cloudflare 403 to our tooling). The FAQ ban on "multiple accounts from the same household, device, or IP address" is in the evaluation list only; `breakout_2` is the only live Breakout account. **The written question for Breakout is still open** (spec 1, § 2.1): *"May I replace my dedicated device with another dedicated Android device or an emulator on the same home network, with my own login? Is any device/IP/fingerprint continuity required for one account, and is a changed device treated as account sharing?"*
- **Only one claimant at a time.** The server pins a device to an account; if the node ever hosts the executor, the phone is retired from `config/prop_phone_devices.yaml`, not run in parallel.

**Bottom line for § 2:** the node *can* plausibly host the executor, but every route has an **unmeasured venue risk** (does Breakout accept this device?) and a **build cost** (3-5 days redroid, 5-10 days browser, ESTIMATED). Do not buy hardware **for** the executor. Buy it for § 3 and treat the executor as a later spike on a box that already exists, after Breakout answers.

## 3. Other jobs a home node is good for

Population note: "today" below means the repo as read on 2026-11-05 (`scripts/ops/`, `.github/workflows/`, `docs/runbooks/liveness-watchdog.md`, `docs/claude/system-actions.md`). I did not audit what pages if **both** VMs are down; that is stated as a gap, not measured.

### 3.1 Independent watchdog and pager (recommended)

- **What exists.** `ict-liveness-watchdog` is an on-VM timer reading `heartbeat.txt`; it dies with the VM. `dashboard-edge-watch` is an outside-in probe from a **GitHub-hosted runner** of the public `ict-bot.duckdns.org` endpoint (Caddy, TLS cert, DuckDNS record); it covers the live VM's public edge only, by its own header. Scheduled GitHub workflows are best-effort (delays are common) and depend on GitHub.
- **Gap.** Nothing independent of **both Oracle and GitHub** watches the system. If the live VM and the trainer VM are both down, or GitHub scheduling stalls, the pager path depends on those same pieces. (The trainer VM's public health has no outside-in probe that I found; **not audited.**)
- **Job.** Every minute, from home: HTTPS probe of the live API's public health route(s), the TLS cert expiry, and DNS resolution; compare to the last state; send **one** page on a state change through a **dedicated Telegram bot** and one recovery. Optionally read the public repo's recent commit time (the repo is public) to detect "git-sync/Actions stalled".
- **Who watches the watcher.** A home power or ISP outage silences the node, which looks like "all quiet". Mitigation, in order of cost: (a) the node sends a heartbeat **to** the live VM's existing device-style endpoint pattern (token-pinned, like `/api/bot/prop/phone/*`), and the existing VM-side or GitHub-hosted watcher alerts on a stale node heartbeat; (b) a UPS on ONT + router + node; (c) a free third-party dead-man service (not verified, not recommended without the operator's OK). The node's pages cover "VMs down"; the existing watchers cover "node down". **Neither covers both failing at once**; say so.
- **Credentials needed:** one Telegram bot token (send-only, a *dedicated* bot, not the existing one). No exchange keys, no diag token if only public routes are probed.

### 3.2 Off-Oracle backup target (recommended)

- **What exists.** `scripts/ops/journal_offvm_backup.py` writes a daily versioned snapshot of `trade_journal.db` to a **private OCI Object Storage bucket** (`ict-journal-backups`, 30 daily + 12 weekly copies). That is off the VM but in **the same cloud tenancy and vendor** as the VMs; an account-level problem with that tenancy takes the VMs and the backups together.
- **Job.** A second copy at home. **Encrypt before it reaches the node** (`age`/GPG to a public key, with the private key held by the operator offline), so the node stores ciphertext it cannot read and a stolen box leaks nothing. Retention mirrored from the bucket; weekly restore-check on a laptop, not on the node.
- **Access path.** The node pulls from an artifact it is allowed to read (the encrypted object), not from the VM. Which store it reads from (a read-only OCI pre-authenticated request, or a second upload from the runner) is a design choice for the build row. **Open.**
- **Why not just local disk on the VM?** Same failure domain.

### 3.3 Local data collection (not recommended now)

No feature currently *needs* a home vantage point for data. The repo rule "off the trade path is not off the data path" applies to features with an owning row and a re-entry test; there is none for this. Do not build speculative collectors. Revisit only when a named consumer exists.

### 3.4 Residential vantage for health checks only

Narrow and allowed: probing **our own** public endpoints (§ 3.1) from a consumer network catches problems a datacenter runner cannot (home-ISP DNS or routing to the duckdns domain, which the SPA's browser-direct path depends on). **Never** used to fetch venue pages on behalf of an executor, to route any VM traffic, to test whether a venue blocks the home address, or to evade a venue's IP rules. If the operator wants any venue reachability check, it is a separate decision.

### 3.5 Things the node should **not** do

Hold exchange or broker API keys; run strategies or order logic; host IB Gateway (it has its own isolated VM); act as a proxy/exit for the VMs (declined 2026-09-30); host the trainer.

## 4. Security model — a third host with credentials

A home node is a new place where secrets can leak, and it sits on a LAN with family devices.

| concern | design |
|---|---|
| **What it holds (minimum)** | Watchdog: one Telegram bot token for its own dedicated bot. Backup: ciphertext only (no key). Later, **only if it hosts the executor**: the dedicated Gmail inbox app password, the Breakout session in the Android data, and the pinned device token. Those are the highest-stakes secrets, which is the reason not to add the executor casually. |
| **Network** | **Outbound only.** No router port-forwards, no inbound listener on the WAN side. Default-deny inbound firewall (ufw/nftables); SSH key-only and reachable from the **LAN only**, for physical-rescue use. Prefer a guest/IoT VLAN if the router supports it (unknown), so a compromised family device cannot reach the node and a compromised node cannot reach the family devices. |
| **Remote access** | Pull-based by default (§ 5), so there is **no inbound path to defend**. Tailscale/WireGuard is an option for ad-hoc SSH but adds a third-party coordination service and a long-lived auth key on the box; not part of the MVP. (The repo mentions Tailscale only in the declined 2026-09-30 plan; nothing is deployed.) |
| **Updates** | Unattended security updates only; scheduled reboot window; image/package versions reported in the heartbeat; kernel and container updates (redroid) by explicit action, never auto. A node that stops reporting its version is itself an alert. |
| **Disk encryption** | Full-disk encryption is at odds with unattended boot. Compromise: the node's own secrets stay minimal and revocable (below), and backups are encrypted independently of the disk. If the executor is ever hosted, revisit (mini-PCs have an fTPM; the Pi has none). |
| **Telegram token scope** | A bot token can send *and* read bot updates; a stolen token can spoof alerts. Dedicated bot, dedicated chat, rotate on loss. |
| **If it is stolen or lost: revocation list** | (1) rotate the node's Telegram bot token; (2) remove the node from any heartbeat/endpoint allowlist; (3) backups: nothing to do, they are ciphertext, the operator holds the key; (4) *only if it ever hosted the executor*: rotate the inbox app password, set the device `revoked: true` in `config/prop_phone_devices.yaml`, and sign the Breakout account out of all sessions / change its password. Keep this list in the node's runbook. |
| **Compromise of the repo** | The pull-based channel (§ 5) trusts `main`, the same trust boundary `ict-git-sync` already extends to the live VM, with the same branch protections. It must not be wider: an **allowlist of named actions, validated parameters, no free-form shell**. |

## 5. Managing it from sessions (so it is not something the operator babysits)

**The existing pattern.** `vm-ops`/`system-actions` run on a GitHub-hosted runner that **SSHes into the VM**, with a fixed allowlist, issue-label triggers, and results posted back to the issue (`docs/claude/system-actions.md` §§ 1, 8). That works because the VMs have public addresses. **A home node does not**, and we do not want to open a router port.

| option | how | pros | cons | verdict |
|---|---|---|---|---|
| **A. Pull-based agent (recommended)** | A systemd timer on the node fetches `main` (as `ict-git-sync` does on the VMs, ~5 min), reads a `home-node/actions/` allowlist file of named actions with parameters, runs only those it knows, and reports status to the live VM's device-style heartbeat route and, on failure, to Telegram. | No inbound path; same trust as git-sync; sessions steer it with ordinary PRs; self-heals. | Latency of a few minutes; needs a small status-ingest route on the VM (Tier-2 when built); results are a status line, not a shell transcript. | **Use** |
| B. Tailscale + runner SSH | Runner joins the tailnet with an ephemeral key and SSHes the node | Interactive, matches `system-actions` | Third-party coordination service, long-lived key on the box, new secret in Actions | later, optional |
| C. Reverse SSH via the live VM | Node dials the VM; runner SSHes VM → node | No new third party | Couples the node to the VM we want it independent of; puts an inbound path into the home LAN on the VM; resembles the declined 2026-09-30 tunnel | **No** |

**No-babysit properties (acceptance for any build row):** `Restart=always` units and the board's hardware watchdog; automatic security updates; heartbeat with version, disk, temperature and last-action result; a stale-heartbeat alert; one-time physical setup (flash or install, plug in power + Ethernet, run one bootstrap command, send the box's public key); a documented rebuild-from-scratch path of under an hour so a dead SD card or SSD is a replacement, not a project.

## 6. Recommendation, cost and questions

**Recommendation: GO on a minimal home node, infra jobs only** (§ 3.1 watchdog + § 3.2 encrypted backup target), managed by the pull-based agent (§ 5, option A).

- **Hardware:** an N100-class mini-PC (16 GB, SSD) at ~$130-220 ESTIMATED, so the executor spike stays possible later without a second purchase; OR a Pi 5 4 GB kit at ~$155 if the operator prefers the cheaper/lower-power board and accepts that the redroid route is unproven there. The infra jobs run on either.
- **Run cost:** ~$6-13/yr in power; optional UPS ~$50-100 ESTIMATED.
- **Build effort (ESTIMATED):** watchdog + heartbeat + pull agent + bootstrap ≈ 2-3 lane-days; encrypted backup pull + restore check ≈ 1-2 lane-days; a status-ingest route on the live VM is **Tier-2** and needs an operator OK in chat when it is built.
- **Not before Breakout answers:** no executor work on the node until the written question (§ 2.2) has a reply or the operator accepts the terms risk in writing.
- **Order:** (1) decide the questions below and buy; (2) one physical setup session; (3) watchdog + heartbeat live; (4) backup target; (5) *only then*, optionally, a redroid spike.

**Questions only the operator can answer**
1. **Home internet:** is your connection behind CGNAT or does it have a public address; roughly how often does power or internet drop? (Decides the "who watches the watcher" mitigation and whether a UPS earns its cost.)
2. **Wired or Wi-Fi:** can the box sit next to the router on Ethernet? (Strongly preferred.)
3. **Hardware preference:** mini-PC (~$130-220, keeps the executor option) or Pi 5 (~$155, cheaper to run, executor route unproven)? Any spare hardware you already own?
4. **Network isolation:** does your router support a guest/IoT VLAN?
5. **Third host:** are you comfortable with a third machine holding a dedicated Telegram bot token now, and (only if the executor ever moves there) the inbox app password later?
6. **Breakout:** do you want to ask Breakout the written question before any executor work, or accept the risk, or paste the Evaluation Agreement so a session can quote it?
7. **Pager:** should the node's pages go to the same Telegram chat as the other system alerts or a separate one?
8. **Budget and UPS:** approve roughly $130-220 for the box (plus optionally ~$50-100 for a UPS) and the ~3-5 lane-days of build?
