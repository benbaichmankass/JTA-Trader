## Cause

The grade's fetch had no 10-28 bars (archive not yet published or incomplete on 2026-11-08; the archive has them now). `ml_decision_entry.features_symbol` / `label_symbol` run positional rolling windows, so a hole is a seam, not a gap:

1. Labels need H contiguous forward bars, so the 10-27 and 10-28 rows vanish (294 rows/day each).
2. Features after the hole span it: on 10-29, `ret_24`, `vol_ratio`, `vol_z`, `breadth_up24` differ for 100% of rows, `xs_rank_ret24` 93%, `ret_1` 98% (a 25h move), `atr_pct` and the labels 50% (ATR spans the hole). `ret_168`, `vol_ratio` and `vol_z` stay corrupted through 11-04 (168 bars); they match again from 11-05.
3. The policy then trades on corrupted inputs for ~7 days, and sequential busy-state diverges.

## Fix

`ml_decision_entry.build_table(..., hole_safe=False)` + `regrid_hourly`: reindex each symbol to a complete hourly grid so a hole becomes NaN bars; rows whose features/labels touch it are dropped, never scored on a seam. Default off so no committed table or grade changes byte-for-byte (no gate; a research-function parameter). On the grade's table `hole_safe=True` keeps 1234 of 3234 window rows (n=167, −0.426) — i.e. the grade's number was computed on rows that should not have been scored. `tests/test_ml_entry_hole_safe.py` (2 tests) covers the seam and the no-hole identity.
